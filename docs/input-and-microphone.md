# RC003-MS 按键映射与麦克风连接

当前 0.2.9（build 16）开发测试候选仅支持 RC003-MS。该设备在蓝牙 Device Information Service 中自报 `MIOM / RC003 / V2.0 / 2671 / A.7.0.6`；已核实 ATVV 服务/特征拓扑，并在不同连接中观察到两种受支持能力响应。0.2.9 将普通 Fn 映射与语音预设统一到同一个软件 Fn 注入器，并新增 Typeless、豆包输入法、微信输入法和闪电说预设。用户已确认上一候选的 Typeless 基本链路可用；新增预设、全部实体按键与原事件屏蔽仍待验收。

下文的 0.1.x 故障和 RC001 是历史证据，用于说明现有权限与音频组件为什么这样设计；它们不表示当前版本仍支持旧型号。安装后请使用 [RC003-MS 安装后验收清单](rc003-ms-acceptance.md)。

## 0.1.x 历史故障

0.1.3 的两个已确认问题：普通用户进程独占 RC001 键盘接口返回 `-536870207 / 0xe00002c1`（权限不足）；音频目录把设备的 Owner 误当成驱动插件，导致已有的专用音频端点被拒绝，连接按钮禁用。

0.1.4 安装后的第一次实体接管又确认了下一层问题：2026-09-01 17:20:02，系统日志记录随机 root 暂存目录中的 `OpenRemoteHIDSessionHelper` 自己请求 TCC，随后明确返回 `TCC deny IOHIDDeviceOpen`。对应界面错误为 `-536870174 / 0xe00002e2`。主程序的输入监控绿勾没有传给这个非 Bundle、随机路径的辅助进程。

## 按键接管

0.2.8 起采用目标项目已经实践的自适应方式：主程序只针对已绑定的 RC003-MS 尝试独占；macOS 拒绝时，以普通权限共享读取同一设备，并在收到遥控器按键报告后短暂屏蔽对应的原系统按键，再发送用户配置的目标键。合成事件带独立标记，不会被再次屏蔽。界面只要求主程序的输入监控与辅助功能，不再启动或检查“遥控器按键服务”，也不请求管理员密码。下方 helper 内容仅保留为旧版本的故障和设计记录。

输入监控和辅助功能授权不包含独占键盘设备所需的管理员权限。Apple 的 [IOHIDLibUserClient 源码](https://github.com/apple-oss-distributions/IOHIDFamily/blob/main/IOHIDFamily/IOHIDLibUserClient.cpp) 在此条件下返回 `kIOReturnNotPrivileged`；[Karabiner 的权限说明](https://github.com/pqrs-org/Karabiner-Elements/blob/main/DEVELOPMENT.md)也明确区分这一要求。原来的“关闭其他按键工具”提示没有区分错误码。

0.1.5 引入固定 bundle identifier `org.rc001remote.assistant.hid-core-service` 的“遥控器按键服务”；0.2.0 保留这些 bundle ID 和安装路径作为原程序的升级身份，不表示支持的硬件仍是 RC001。安装包内保留签名模板，实际执行的同字节副本位于 root 保护的 `/Library/PrivilegedHelperTools/OpenRemoteHIDCoreService.app`。辅助进程只接管固定 VID/PID、蓝牙键盘接口及用户已确认的本机 RegistryID/LocationID。必须只有一个符合条件的设备，不自动选择另一只。

0.2.1 的普通权限检查仍由主程序用 `Process` 直接启动固定 helper。实机 TCC 记录表明，这次检查被归到主程序，而不是“遥控器按键服务”自身，因此旧界面不能把该结果当作 helper 已获得输入监控的证据。0.2.2 改由 LaunchServices 将 root 保护路径中的固定 helper 作为独立应用启动。主程序用 LaunchServices 返回的精确实例 PID 锚定会话；双方通过私有 Unix socket 核验审计令牌、用户、启动身份、固定路径和运行代码 CDHash。helper 在首次完整核验后才用 `SecRandomCopyBytes` 生成 256-bit 随机挑战；主程序严格接收一次挑战、再次核验 helper、回显挑战及自己的 nonce 后结束写方向。helper 只在收到一个完整请求、确认没有半帧或额外帧，并立即复验发送者完整 audit token 和 PID version 后，才执行 `check` 或 `request`。操作、两个随机值和结果路径不出现在启动参数、环境变量或文件中；开发签名的 helper 也启用 hardened runtime，构建与打包拒绝可放宽动态库注入保护的代码签名权限。任何同用户但不是固定主程序的进程都不能让 helper 调用 `IOHIDRequestAccess`。这使本机测试可逐段观察 TCC 归属和返回值；它不证明同一路径在管理员会话中一定继承用户侧授权。

界面分别显示主程序输入监控、主程序辅助功能、按键服务用户侧输入监控，以及后续管理员接管结果。按键服务权限不能由主程序的两项绿勾推断。未通过时不先请求管理员密码；用户明确点击检查或请求后，LaunchServices 才启动固定 helper，由它检查或发起系统权限请求。打开“隐私与安全性 → 输入监控”是另一个明确动作，系统设置里预期显示“遥控器按键服务”。授权结果未知或被拒绝时不会自动反复请求管理员授权。

按键服务只回传程序允许的遥控器用法集合。它不采集其他键盘、音频，不发送设备控制报告，不执行外部命令，也不注入系统按键。按键注入和语音仍由普通权限主程序完成。RC003-MS 的真实按键报告和每个实体键的键值仍需用户测试，不沿用 0.1.x 旧遥控器的“十个键已验证”结论。语音键通过独立 GATT 通道处理；只使用遥控器麦克风不需要按键接管的管理员授权。下文的语音软件预设也不启动这套完整按键接管，只使用主程序辅助功能权限发送软件 Fn。

用户侧权限检查和管理员按键会话都采用当前用户私有目录中的 Unix socket。双方检查对端账户/PID、审计令牌与启动时间，并核验固定安装位置、版本和代码签名/CDHash。一次随机令牌绑定一次会话；消息有长度、白名单和顺序校验。权限检查超时或取消后会关闭通信并请求结束精确的 LaunchServices 实例，但在确认该实例退出前仍阻止下一次检查或管理员会话。只有按键服务用户侧授权明确允许，并且管理员运行的同一 helper 对指定 RC003-MS 真实 `Seize` 后通过已认证会话返回 `ready`，界面才显示映射已启用。LaunchServices 启动完成、主程序权限为允许、管理员对话框完成或 helper 文件校验通过，均不能替代这两个运行阶段。

停止、退出、断连和异常会停止输出并释放设备；独立看门狗以约三秒的失联窗口终止本辅助进程，避免 UI 或 IOKit 调用卡住时长期占有设备。此时间不是操作系统任意调度/内核故障下的硬实时保证。一次按键会话最长八小时，到期须再次手动启用。主程序等待辅助进程退出或释放确认后才允许再次启用；状态不明时提供“检查停止状态”，不会自动重复授权。退出等待超过六秒时，用户可以返回检查或知情退出。

不增加 LaunchDaemon、登录项或常驻进程，不保存管理员密码。按键服务有一个公开且固定的第三安装目标；其父目录及 bundle 均须 root:wheel 且普通用户不可写。普通权限与管理员执行都核验固定路径、逐级所有权和 ACL、签名标识、主程序版本和构建号、应用内模板，以及主程序 Info 中的 SHA-256。0.1.5 不再把它复制到随机 root 临时目录。每次会话的 Unix 通信目录仍由普通应用清理；不执行对任意路径的递归删除。

macOS 的主程序输入监控、按键服务用户侧输入监控和管理员 HID 权限是独立条件，管理员权限本身也不等于设备已成功 `Seize`。程序不会关闭系统保护或改成共享读取来掩盖拒绝。0.2.2 的 LaunchServices 独立身份、root helper access 和 RC003-MS 独占仍须安装后验证；在真实 `ready` 返回前，界面不能声称映射已启用。若 root 阶段仍返回 `0xe00002e2`，本次 LaunchServices 假设即判失败，应保留证据并转入正式签名的系统服务方案探针，不能循环刷新权限或宣称已修好。

当前 0.2.9 开发包使用 ad-hoc 签名，只能作为这一份二进制在这台 Mac 上的可证伪测试；应用签名改变后，macOS 可能要求重新批准主程序权限。当前不纳入 `SMAppService`、LaunchDaemon 或管理员按键会话。

面向他人的开源发行版必须使用稳定 Team ID、Developer ID Application / Installer 签名并公证，再在干净 macOS 26 环境做完整实体测试。必须逐键取得共享 HID 报告、原事件屏蔽和目标输出证据。0.2.9 没有注册 LaunchDaemon、登录项或其他常驻服务，也不把尚未完成的实测写成生产结论。

## 语音软件快捷键预设（默认关闭）

Typeless 和闪电说“直接说”使用短点 Fn 切换一次语音输入会话；豆包输入法、微信输入法及闪电说“帮我说”使用按住 Fn 说话。RC003-MS 的物理语音键同时会在键盘 HID 接口报告 F5。若直接把这段物理 F5 映射成 Fn，它会与预设生成的 Fn 事件互相干扰。程序因此用 macOS `UserKeyMapping` 把 F5（usage page `0x07`、usage `0x3e`）映射到 usage 0，只丢弃这只遥控器的物理 F5 两个边沿；遥控器麦克风的 ATVV 控制和音频通道继续工作。

中和是一次事务，范围限定为用户已绑定 RC003-MS 的 LocationID，并要求该位置的每一个匹配 HID 服务都成功写入。只找到部分服务、缺少身份或任一写入失败时，程序回滚已经修改的服务并保持预设未就绪。每次真实语音流开始前还会重新枚举和核验全部服务；复核失败就立即关麦，不发送 Fn 或声音。关闭预设、改变设备绑定、发生注入失败或退出应用时，会取消待执行任务、结束或清理当前会话，并恢复启用前保存的 F5 映射。

点按模式复核通过后先保留有界 pre-roll，短点一次 Fn 成功后才送出缓存并继续送音；遥控器松开时先等待已入队音频正常排空，最长 0.75 秒，再短点一次 Fn 结束。长按模式在发送开麦命令前按下 Fn，松开遥控器后先送完尾音再释放 Fn。快速连续会话使用独立代次隔离；切换模式、失败、断连和退出都会补做平衡释放。开始事件失败时不会放出音频，结束事件失败时会关闭预设、恢复遥控器原映射并显示错误。

预设只需要给主程序“遥控器助手”授予辅助功能权限，用于发布软件 Fn 事件。它不需要主程序输入监控、“遥控器按键服务”输入监控、管理员授权、HID `Seize` 或开启顶部完整按键映射。用户仍须在目标软件自己的麦克风菜单里选择 **“遥控器麦克风”**，并允许它使用 macOS 麦克风；助手不能替目标软件选择内部设备。普通麦克风转接不依赖预设。

软件 Fn 使用 macOS 虚拟键码 63：按下时携带 `maskSecondaryFn`，释放时清除该标志，CoreGraphics 对两者呈现为 `flagsChanged`。普通“映射为 Fn”和语音预设共用这一个 `hidSystemState` 注入器。它提供 macOS 事件层的 Fn 语义，但不是实体键盘的 Globe 开关；只监听原始 HID 的程序仍可能不接受，因此各目标软件须实测。

事务式 F5 中和、软件 Fn 注入和成对 Fn 点按会话控制直接适配自 [HD838A/remote-mic-app 固定提交 `9e019112fc88534004641499b0b1efc50b491e5e`](https://github.com/HD838A/remote-mic-app/tree/9e019112fc88534004641499b0b1efc50b491e5e)，版权归 2026 SayAll contributors，许可为 GPL-3.0-only。本项目增加了已绑定 LocationID 范围、每流复核、独立 OpenRemoteAudio 路由、长按会话和多软件预设；没有复制该项目的品牌名、bundle 标识、二进制、Logo、App Icon 或商品照片。用户已确认 Typeless 基本链路可用，新增预设仍须逐项实测，详见 [RC003-MS 验收清单](rc003-ms-acceptance.md)。

## 麦克风连接

在本次 macOS 实机上，两个专用端点的 Owner 是 AudioSystem 对象，不是插件对象。0.1.4 改用系统的 bundle ID → 插件查询，再由插件分别按 UID 查回输入和隐藏输出，要求与系统解析的两个设备完全一致。0.2.5 继续核验名称、UID、厂商、在线状态和双向通道，并要求公开输入为 USB-compatible transport、隐藏写入端为 Virtual；属性读取失败不能作为“零通道”通过。

修正后，同一组已安装的专用端点通过只读校验。按键服务的 TCC 问题不需要通过重载音频、重新安装其他驱动或重启电脑处理。只有新驱动已安装但专用端点尚未生效时，才按界面提示由用户确认重新加载音频服务。

系统里能选择“遥控器麦克风”只表示公开输入存在。必须在助手中点击“连接遥控器麦克风”，等待遥控器连接，然后按住右上角语音键说话，才会有数据输入。接收软件仍须具备自己的麦克风权限；若它在安装或音频组件生效前已经打开，可能需要完全退出并重新启动，才会刷新设备菜单。0.2.2 起在首次点击连接时等待一次新的系统音频设备目录检查完成，再判断专用输入与隐藏输出，修复旧状态刷新未结束时按钮误判或首击失败的竞态；这项修复不替代真实声音验收。

界面分别显示组件、遥控器连接和音频状态。只有完整 PCM 帧成功送入专用输出才显示已收到音频；语音开始事件本身不算收到声音。连续两秒未收到完整帧会停止服务并请求关麦，给出错误。收到全零 PCM 也算数据到达，避免把安静间隙误判为断流。松开语音键会请求关麦，并按正常路径排空已经进入 Mac 的有界尾音；程序不录音、不转写、不上传，也不调用电脑麦克风。

0.2.2 实机按下语音键后已收到并入队完整 PCM 帧，但松开时主线程在 `AudioQueueDispose(true)` 内等待同一主队列上的缓冲回调，导致界面彩球并阻断后续关麦命令。0.2.3 把 AudioQueue 回调移到独立串行队列，旧回调异步回主线程后先核对代次和队列身份；停止时主线程先摘除旧队列，再由另一个后台串行队列同步销毁。活动和待销毁队列总数限制为两个，异常销毁时不再继续无界创建。

0.2.4 增加兼容只跟随系统默认输入的软件的明确操作。安装、重载、连接遥控器都不会自动更改默认设备；只有用户点击“设为系统默认输入”并确认后，程序才请求把“遥控器麦克风”设为系统默认输入。该操作只改默认输入，不改默认输出或系统输出，并保存操作前输入设备的 UID；界面等待 CoreAudio 的属性变化通知并回读结果，不把写入调用返回当作切换已经生效。恢复也只由用户明确触发，而且仅在当前默认输入仍是“遥控器麦克风”时执行。若状态刷新检查到用户或其他软件已改选输入，程序清除旧恢复记录，不再用它恢复。退出不会静默切换默认输入：仅当界面已确认“遥控器麦克风”仍是系统默认输入且存在有效恢复对象时，才显示“恢复原输入并退出”（默认）、“保留并退出”和“取消退出”；恢复失败时再显示“返回检查”或“保留当前输入并退出”。其他状态直接保持当前默认输入并退出。能够在设备菜单中直接选输入的软件仍应直接选择“遥控器麦克风”。

0.2.5 根据 [HD838A/remote-mic-app](https://github.com/HD838A/remote-mic-app) 的公开实现与故障记录，补上 transport 枚举兼容。部分目标软件在 CoreAudio 目录中排除普通 Virtual 设备，因此即使系统和 FFmpeg 能打开输入、甚至把它设为默认，目标软件的设备菜单仍可能没有它。新版只让用户可见的输入端报告 USB transport 兼容元数据；应用写入的隐藏输出仍为 Virtual，分离端点、PCM、名称、UID 和默认设备行为都不改变。这不是实体 USB 设备声明。驱动和应用同时校验这组精确组合，旧驱动与新应用混装时不会误报就绪。对方项目采用单个双向回环设备，本项目没有复制其拓扑、标识、二进制或图标。

同一次审阅还发现正常 `STREAM_STOP` 后立即销毁 AudioQueue 会丢弃已到达 Mac、但尚未送完的尾音。0.2.5 的正常松键路径改为 `AudioQueueStop(false)`，轮询只读 `IsRunning`，确认已停止后才在后台销毁；最长等待 0.75 秒，状态不可读或超时即强制回收。错误、断连、退出和新会话抢占仍立即停止，活动与待释放队列合计最多两个。音频电平的 SwiftUI 发布从逐帧降低到最多 20 Hz，首帧仍立即显示，避免每秒约 67 个音频帧引起不必要的界面重绘。这些改动只能保护已经进入 Mac 的 PCM，不能补回遥控器固件在松键时尚未发送的数据。

0.2.6 的本机现场确认：磁盘新驱动已经安装，但 CoreAudio 仍完整驻留 0.2.4 的 Virtual/Virtual 双端点。主程序连续只读检查能稳定识别为 `previousVirtualInput`，原管理员工具却把两个 UID 均存在当成异常，导致重载请求从未发送。新版让管理员工具独立核验同一组完整指纹，并只为这一精确旧组合或双端点均未注册的情况允许一次重载；半残、陌生、身份不符或查询失败继续拒绝。发送方式保留唯一 PID、Apple 签名、系统账户、父进程、固定路径和启动时间核验，并采用与参考程序一致的正常 `SIGTERM` 语义，不按名称批量终止、不回退强杀。

目录检查、设备身份、两种白名单 ATVV 能力响应、解码测试、成功入队、USB-compatible transport，以及 AVFoundation/FFmpeg 成功打开公开输入，仍不能替代“RC003-MS 遥控器说话 → 系统输入 → 接收软件”的真实验收。用户已确认 Typeless 基本链路可用，但开头、尾音、快速连续会话、故障清理和退出恢复仍应形成逐项记录；豆包输入法、微信输入法和闪电说预设尚未取得实机结果。
